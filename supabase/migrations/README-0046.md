# 0046 — Плащане по видео

Заменя начисляването по етап от 0040/0041. Единицата е **(видео × човек × роля)**,
уникална в базата — не етап.

## ⚠️ ПРЕДИ да пуснеш — провери едно нещо

Отвори секция 1 на `0046_video_pay.sql` и виж таблицата `stage_roles`.
Тя допуска реалните ти `stage_key` стойности от `lib/data.ts`:

`strategy · script · shoot · edit · review · publish · copy · design`

**Ключовият ред е `('review','editor')`** — преглед и монтаж стават ЕДНА платена
роля, значи ЕДИН ред за видео. Точно това маха дубликатите (4 реда за 2 видеа).
Същото важи за `('design','poster')` при постовете.

**Ако не искаш да плащаш публикуването** — изтрий реда `('publish','publisher')`.
Етап без ред в `stage_roles` не струва пари.

## Пускане

```bash
psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f web/supabase/migrations/0046_video_pay.sql
```

Идемпотентна е — безопасно е да се пусне пак.

## Какво прави с наличните данни

Свива `task_pay` в `video_earnings`. Цената на свития ред е **max(старите суми)**,
не сборът — иначе човекът получава двойно за една и съща работа. Вече платените
се затварят с наследствено плащане (`method='legacy'`), за да не изскочат като
дължими.

Проверено на реален случай: 5 стари реда (€50) → 3 реални (€30).

Старите тригери `trg_fill_task_pay_*` се махат. Таблицата `task_pay` **остава**
като архив — нищо не се трие.

## Правила, зашити в модела

- **Дължимо** е, щом човекът си свърши своята част (всичките му задачи по тази
  роля за това видео са `done`). Не се чака публикуване или одобрение от клиента.
- **Пакет** (N видеа за X€) се плаща наведнъж при завършване. Видеата вътре само
  придвижват прогреса и никога не стават поотделно дължими.
- **Цена** — различна по човек, роля и клиент. Приоритет: клиент(4) + роля(2).
- **Смяна на цена** = нов ред във `video_rates` с `valid_from`. Заработените си
  пазят цената. Ръчна цена на конкретно видео се заключва (`price_locked`).
- **Плащане** е ред в `payouts` с дата, метод и референция. Отменяемо.

## Функции за фронтенда

```ts
rpc('bm_video_price',     { p_profile, p_role, p_client })
rpc('bm_set_rate',        { p_profile, p_price, p_role, p_client })
rpc('bm_set_video_price', { p_earning, p_price })
rpc('bm_pay_videos',      { p_profile, p_earnings, p_packages, p_method, p_reference, p_note })
rpc('bm_pay_all',         { p_profile, p_method, p_reference, p_note })
rpc('bm_undo_payout',     { p_payout })
rpc('bm_create_package',  { p_profile, p_target, p_total, p_label, p_role, p_client })
```

Четене: `v_worker_owed` (редът на човека), `video_earnings` (детайлът),
`worker_packages` (прогрес), `payouts` (историята).

## Достъп

Всички парични таблици са с RLS: чете ги **админът или самият човек**, пише ги
само админът. `v_worker_owed` носи филтъра вътре във view-то (в PG14 view-тата
не прилагат RLS на подлежащите таблици).

## Тествано

Postgres, два последователни пробега без грешки. Покрити сценарии:

| Сценарий | Очаквано | Резултат |
|---|---|---|
| 4 задачи / 2 видеа | 2 реда, не 4 | ✅ |
| едно видео, две роли | 2 реда, €15 + €10 | ✅ |
| задача върната от done | дължимото пада | ✅ |
| ръчна цена €18 vs тарифа €25 | €18 оцелява | ✅ |
| частично плащане 1 от 3 | остават 2 дължими | ✅ |
| отмяна на плащане | дължимото се връща | ✅ |
| пакет 2/3 → 3/3 | €0 → €45 | ✅ |
| пренасочване към друг човек | парите се местят по неговата тарифа | ✅ |
| пренос от task_pay | €50 в 5 реда → €30 в 3 | ✅ |
